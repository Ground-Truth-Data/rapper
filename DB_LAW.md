The user's data is never thrown away and the app never waits.
1. A local file an older build made (it lacks a table or column today's DDL declares) is never migrated. Signed in: keep it aside as `*.unsent-*`, open a fresh file, and the account's cloud copy fills it; after every pull the kept file's rows the copy lacks merge in, and it is deleted only once an upload holds them. A kept file the merge refuses stays and alarms `pullAccount:unsentRefused`. A copy a newer build or a newer Central made merges the columns both hold; a column this phone lacks never blocks it. Signed out (or a sandbox world): copy its rows into a fresh file and keep the older file aside as `*.older-*`. The older tab can write to it until its lock is stolen, so every later signed-out open copies it again (a key the live file holds keeps its row) and deletes it once it holds no row the live file lacks. A signed-in open never reads it. A live file stamped with another account than the one signing in is moved aside as `*.account-<owner>-*` and a fresh file opens; only the owner's own pull merges it back, then uploads it, and it goes once an upload holds its rows.
2. Broken local file (corrupt/unreadable): set it aside, never delete it, and download the current file from Supabase. On sign-out, a set-aside broken file is erased too.
3. No account and broken file: start fresh and alarm `sql:setAside`. Nothing on screen — no line, no banner.
4. Newest tab always takes the database immediately. No waiting on other tabs, locks, or old copies. Never a 'open in another tab' screen.
5. Schema changes are add-only: add tables and columns, never delete. A column leaves in two steps: first a build that stops writing it ships, while the phone schema and Central both keep the column, unwritten; then both drop it, only once no app in use still sends it, after the startup version check has turned older apps away. A rename is an add, then that two-step removal. Before every ship, `getCache/scripts/oldBuildUpload.mjs` uploads a file from the build getCache main is at, every table and column filled, and Central must hold all of it (4 Nov 2026, after a one-step drop discarded old phones' `seedlot`). Adding never needs a new version or a new file.
6. Never an empty screen when data exists, never a silent spinner.
7. One page, one database worker. A second copy of open.ts reloads the page. Gate stage "tabs" (newestTabWins.spec.ts) proves it. The app never retries or waits; the test may poll until the old worker lets go of the file (Chris, 4 Nov 2026).
8. The one retry: a transaction a newer tab cuts is rolled back whole, and the older tab redoes it silently once it has the file back (`alone()` in open.ts).
9. A file something live still holds (SQLITE_BUSY) runs the tab on memory and alarms `sql:memory`; on each later focus the tab tries the file once and moves onto it when free. What it wrote on memory merges into the file there, and the file's self stays self (`mergeMemory`). A frozen tab never holds the file (`busyHolder.spec.ts`).
10. Sign-out erases the local file: a chosen sign-out, a session ended elsewhere and 30 days without a sign-in all go through `eraseLocal()` (getCache `snapshotUploader.ts`). Unsent rows upload first, a kept `*.unsent-*` file's included; if they cannot, nothing is erased and the device stays signed in. A write landing during the sign-out itself keeps the file, stamped with the departing account before sign-out begins (law 1 says where it goes).
11. The plugins file (`getcache-plugins.sqlite3`) belongs to the phone, not to an account: a plugin is added from a link with no sign-in, and its answers leave only as a file the planter sends. Sign-out never erases it, and no cloud copy refills it.
